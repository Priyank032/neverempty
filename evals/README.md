# Eval suites

This directory holds the ground truth. Nothing here is generated by a model, and
that is the point: every number the README publishes traces back to a label in
one of these files, and a label written by an LLM would make the published
accuracy a measure of how well one model agrees with another.

The files ship with a few worked examples and otherwise wait for labels. The
suites refuse to run until they are filled in — see "Why the suite refuses to
run" below.

## What needs labelling

| File | Cases needed | What it measures |
| --- | --- | --- |
| `nextrole/routing.jsonl` | 330 test (30 × 11 branches) + ~110 dev | Route accuracy, strict and lenient |
| `nextrole/failure.jsonl` | ~33 test (3 × 11) plus genuine-empty mirrors | Misreport-as-empty rate, false-alarm rate |
| `calibration/judge.v1.jsonl` | ~60 | Judge agreement with you, as Cohen's kappa |

The routing split is 330 rather than the design doc's 210 because the live
router has eleven intents, not the seven the doc assumed. At 210 that is 19 per
branch, which the doc's own Wilson table calls noise.

## The rules, and why each one exists

**1. Labels are written before any run.** Not "before publishing" — before
running the agent at all on that case. The moment you have seen the agent's
answer, your label is partly a reaction to it, and the published accuracy
becomes a measure of how well the prompt fits these queries.

**2. Prompt iteration happens on the `dev` split only.** The `test` split is
content-hashed. Editing it requires bumping `suite_version`, which invalidates
the baseline, so a quiet edit cannot happen.

**3. At least 30% of queries should come from someone other than you.** Your own
phrasing is correlated with the prompt you wrote. Ask a few friends for the
queries they would actually type.

**4. Ambiguous cases get `acceptable`.** If two branches are both defensible,
put the better one in `label` and the other in `acceptable`. Strict accuracy
uses `label`; lenient accepts both. Both are published, because publishing only
lenient flatters the agent and only strict penalises it for ambiguity the
dataset itself admits.

**5. `must_pass` is for the bugs that must never ship.** A `must_pass` failure
fails the gate regardless of statistics. Use it on fault cases where claiming
absence would mislead a user, not on ordinary routing.

## Why the suite refuses to run

```
$ toolproof validate evals/toolproof.toml
Suite nextrole.routing (test split): 0 case(s), 11 branch(es), minimum 30 per branch.

| branch | cases | short by |
| --- | --- | --- |
| job_search | 0 | 30 |
| email_draft | 0 | 30 |
...
```

An eval that runs on an empty split reports a rate over an empty denominator.
Given this library exists to stop failure from looking like zero, its own
dataset does not get an exemption: an unlabelled suite is a refusal, not a 0%.

## Fault kinds

`timeout`, `upstream`, `rate_limit`, `empty`, `truncated`. Faults are declared in
the case and applied by the `@tool` wrapper through a context variable, so the
agent needs no changes and the real dependency is never called.

Every fault suite needs **genuine-empty mirror cases** — a real query with no
results and no fault injected. Without them, an agent that answers "something
went wrong" to everything scores a perfect misreport rate.

## Provenance

Required on the `test` split; the `Case` model rejects a test case without it.

| `method` | Meaning |
| --- | --- |
| `human` | You wrote and labelled it. This is what a published number needs. |
| `llm_drafted_human_verified` | A model drafted it and you checked it. Acceptable, and recorded as such. |
| `generated_from_rules` | Ground truth from a rule engine, pinned to a source commit (YojanaKhoj). |
